# Warehouse — เอกสารส่งต่องาน Frontend

วันที่: 5 ตุลาคม 2026  
อ้างอิง: โค้ดใน working tree ของ branch `be` ณ วันที่เขียนเอกสาร

เอกสารนี้เขียนใหม่สำหรับ FE ที่จะนำ API ของ BE รอบปรับประสิทธิภาพไปใช้ เป้าหมายคือโหลดข้อมูลตามหน้าที่ใช้งาน ลดการดึงรายละเอียดที่ไม่จำเป็น และลดการโหลดซ้ำ โดยรักษาขั้นตอนรับสินค้า การลงสต๊อก สิทธิ์ และ business logic เดิม

**สถานะ:** BE เพิ่ม API options และ route stock แล้ว ส่วนงาน FE ด้านล่างเป็นงานที่ต้องนำไปทำต่อ ตัวอย่างชื่อ wrapper ใหม่เป็นข้อเสนอ ยังไม่ได้เพิ่มใน `warehouseApi` และสถานะ working tree ไม่ได้ยืนยันว่าโค้ดถูก commit/push ไป remote แล้ว

## 1. สิ่งที่ BE พร้อมให้ FE ใช้

| ความสามารถ | ใช้กับงานใด | ผลที่ได้ |
|---|---|---|
| PO list: `closed=true/false` | selector PO ที่ยังเปิดอยู่ หรือรายการแยกสถานะ | กรองก่อนแบ่งหน้า ไม่ต้องดึงรายการปิดมาแล้วทิ้งที่ FE |
| Carrier list: `received=true/false`, `hasGoodsReceipt=true/false` | selector ใบขนส่งที่พร้อมนับ | กรองเอกสารที่รับแล้วและยังไม่มีใบตรวจรับก่อนแบ่งหน้า |
| Warehouse catalog: `branchId` | เลือกคลังในสาขาที่รับจริง | ลดข้อมูลคลังที่ไม่เกี่ยวข้อง โดยยังตรวจ branch scope เดิม |
| PO detail: `view=lines` | ฟอร์มใบผู้ขายและฟอร์มนับ | ส่ง header + lines โดยไม่โหลดเอกสารเกี่ยวข้องและ revisions |
| Carrier detail: `view=confirmation` | ฟอร์มนับที่ต้องรู้สาขารับและ PO | ส่ง header + confirmation โดยไม่โหลด lines, media, revisions |
| Catalog: `lookup=1` เพิ่มครบทุก kind | dropdown/search selector | ส่งเฉพาะคอลัมน์สำหรับเลือก สูงสุด 50 รายการ |
| `POST /api/stock/documents` | จ่าย ปรับ โอนสต๊อก | เชื่อม HTTP route เข้ากับ stock service เดิม |
| `POST /api/stock/documents/{id}/reverse` | กลับรายการ | เชื่อม HTTP route เข้ากับ reversal service เดิม |

คำขอเดิมที่ไม่ส่ง options ใหม่ยังใช้ response, ordering และ pagination เดิมได้ ไม่มี package ใหม่ที่ FE ต้องติดตั้งเพื่อเรียก API เหล่านี้

**แยกผลให้ถูก:** compact view ลด payload และจำนวน business query ภายในหนึ่ง HTTP request; การลดจำนวน HTTP requests ต้องเกิดจากจังหวะโหลด การใช้ข้อมูลร่วมกัน และการ refresh ของ FE ด้วย การจัดกลุ่มชื่อเมนูอย่างเดียวไม่ได้ลด request

|---|---|---|---|
| PO | PO 1 | suppliers + CEOs 2 | 3 |
| ผู้ขาย | PO + supplier receipts 2 | ไม่มี | 2 |
| ขนส่ง | PO + carriers 2 | branches 1 | 3 |

## 3. สัญญา API ที่ FE ต้องใช้

### 3.1 PO list: สถานะปิดและการค้นหา

```http
GET /api/purchase-orders?closed=false&limit=20
GET /api/purchase-orders?closed=false&q=PO-00000012&limit=20
GET /api/purchase-orders?closed=true&limit=20
```

- `closed=false`: `closed_at` เป็น null; `closed=true`: มีเวลาปิด
- ไม่ส่ง `closed`: รวมทั้งเปิดและปิดตามพฤติกรรมเดิม
- การยังเปิดอยู่ไม่ได้แปลว่ามีจำนวนค้างรับ ต้องใช้ข้อมูล quantity/report ตามงานนั้น
- `q` ค้นเลข PO ไม่ใช่ชื่อผู้ขาย ตัด whitespace และยาวไม่เกิน 100 ตัวอักษร
- ใช้ `closed=false` กับ selector ในฟอร์มผู้ขาย/ขนส่ง; รายการประวัติ PO ยังควรแสดงทั้งสองสถานะ เว้นแต่ผู้ใช้เลือก filter
- คำขอ search และ load more ต้องส่ง filter ชุดเดียวกับหน้าแรก

### 3.2 Carrier list: ตัวเลือกสำหรับนับ

```http
GET /api/carrier-receipts?received=true&hasGoodsReceipt=false&limit=20
GET /api/carrier-receipts?received=false&limit=20
GET /api/carrier-receipts?hasGoodsReceipt=true&limit=20
```

- `received=true`: มี `delivery_confirmations.received_at`
- `received=false`: ไม่มีเวลารับ รวมถึงเอกสารที่ยังไม่มี confirmation
- `hasGoodsReceipt=true`: มี goods receipt ที่อ้าง carrier นี้อย่างน้อยหนึ่งรายการ
- `hasGoodsReceipt=false`: ยังไม่มี goods receipt อ้าง carrier นี้
- existence ของ goods receipt ไม่ได้กรอง posted/reversed state; ห้ามตีความว่า reverse แล้วกลับมานับซ้ำได้
- ไม่ส่ง filter ใด จะไม่จำกัดเงื่อนไขนั้น
- Carrier list รอบนี้ไม่ได้เพิ่ม `q` search; อย่าสร้าง wrapper ที่สมมติว่า server ค้น carrier ด้วย `q` ได้

ใช้คำขอแรกกับ selector ใน CountForm แทนการโหลด carrier หน้าแรกทั้งหมดแล้ว filter `received_at`/`has_goods_receipt` ที่ FE เพราะหน้าแรกอาจมีแต่เอกสารที่เลือกไม่ได้ แต่หน้าถัดไปมีตัวเลือกที่ใช้งานได้

อย่านำ filter นี้ไปใช้กับรายการประวัติ carrier ในแท็บขนส่งทั้งหน้า เพราะจะซ่อนเอกสารที่ยังรอรับหรือเคยนับแล้ว

### 3.3 Compact detail: ต้องแยกจาก full detail

```http
GET /api/purchase-orders/12?view=lines
GET /api/carrier-receipts/34?view=confirmation
```

| View | ฟิลด์หลักที่ได้ | ฟิลด์ที่ไม่ถูกส่ง |
|---|---|---|
| PO `lines` | header เดิมทั้งหมด + `lines` | `supplierReceipts`, `carrierReceipts`, `goodsReceipts`, `revisions` |
| Carrier `confirmation` | header เดิมทั้งหมด + `confirmation` (object หรือ null) | `lines`, `media`, `revisions` |

PO lines ยังคำนวณ quantity เหมือนเดิมสำหรับ role ที่ได้รับข้อมูลนั้น: `supplier_quantity`, `carrier_document_quantity`, `counted_good_quantity`, `damaged_quantity`, `wrong_quantity`, `posted_good_quantity`, `remaining_good_quantity` และฟิลด์สินค้า/ราคาเดิม ไม่ต้องนำไปคำนวณสูตรใหม่ที่ FE

EMPLOYEE ได้ line projection เดิมเฉพาะ `id`, `purchase_order_id`, `product_id`, `quantity`, `sku`, `product_name`, `unit_code`; อย่ากำหนด type ว่าราคา/quantity aggregates ต้องมีในทุก role

ไม่ส่ง `view` หรือส่ง `view=full` จะได้ detail เต็มเดิม ค่าว่างหรือ view ที่ไม่รู้จักได้ 400

**ห้ามใช้ compact แทน full ทุกจุด:**

- `PoDetails` ใช้ความยาวของเอกสารผูกเพื่อตัดสินการแสดงฟอร์มแก้ไข การไม่มีฟิลด์ใน compact response ไม่ได้หมายถึงไม่มีเอกสารผูก
- `CarrierDetails` แสดงหลักฐานจาก `media` ซึ่ง compact ไม่มี
- ถ้าเก็บ detail ใน state/cache ให้แยก key ตาม `id + view` และอย่าให้ compact เขียนทับ full แล้วทำข้อมูลอื่นหาย

จำนวน business query ของ PO ลด 6 → 2 (EMPLOYEE 3 → 2); carrier ลด 5 → 2 ตัวเลขนี้ตรวจจาก mock query calls ไม่รวม auth/actor lookup และไม่ใช่ผลวัด latency ฐานข้อมูลจริง

### 3.4 Catalog lookup และ branch filter

```http
GET /api/catalog/suppliers?lookup=1&q=บริษัท
GET /api/catalog/branches?lookup=1
GET /api/catalog/warehouses?lookup=1&branchId=7&q=คลัง
GET /api/catalog/warehouses?page=1&limit=20&branchId=7&q=คลัง
```

| Kind | คอลัมน์ lookup |
|---|---|
| branches | `id, code, name, active` |
| warehouses | `id, branch_id, code, name, active` |
| suppliers | `id, code, name, active` |
| units | `id, code, name` |
| product-groups | `id, name` |
| product-categories | `id, group_id, name` |
| brands | `id, name` |
| product-models | `id, brand_id, name` |
| products | `id, sku, name, unit_id, serial_tracked, active` |

- Lookup คืน array ใน `data` สูงสุด 50 ไม่มี `page`, total หรือ cursor ใช้ `q` ที่ยาวไม่เกิน 100 เพื่อค้นเพิ่ม
- branches/warehouses/suppliers/units ค้น code หรือ name; กลุ่ม/หมวด/ยี่ห้อ/รุ่นค้น name; products ค้น SKU หรือ name
- products คง active-only และเรียง SKU, ID เดิม; lookup อื่นเรียง ID จากใหม่ไปเก่า และไม่ตัด inactive อัตโนมัติ
- ฟอร์มที่เดิมเลือกเฉพาะ active ให้คงเงื่อนไข `active !== false`; ตัวกรองประวัติอาจต้องมี inactive จึงห้ามกรอง active ทุกบริบทเหมือนกัน
- **อย่าส่ง `page` กับ `lookup=1`** ถ้าต้องการ compact selector เพราะเมื่อมี `page` route จะใช้ paginated catalog เดิม
- `branchId` ใช้กับ warehouses ในทั้ง legacy list, lookup และ paginated list; เป็นการตัดกับ scope เดิม สาขาที่อยู่นอก scope จะได้รายการว่าง
- catalog โดยไม่ส่ง `page`/`lookup=1` ยังเป็น legacy list สูงสุด 500 ตามเดิม

**อย่าเปลี่ยน static select จาก 500 เป็น lookup 50 แล้วถือว่าเสร็จ:** dropdown ต้องค้นรายการนอก 50 แรกได้ หรือใช้ catalog page พร้อม load more; ไม่เรียก lookup ด้วย cursor เพราะ API นี้ไม่มี cursor

เมื่อแก้ไขข้อมูลเดิม ต้องรักษา option ที่เลือกไว้ แม้ option นั้นไม่อยู่ในผลค้นหาปัจจุบัน/50 แรก เก็บ label จากข้อมูลที่มีหรือ reference ที่เคยโหลด อย่าสมมติว่ามี catalog detail GET ใหม่สำหรับหา option ตาม ID

### 3.5 Response, pagination และ validation

```json
{
  "data": [{ "id": 12, "record_no": "PO-00000012" }],
  "page": { "limit": 20, "hasMore": true, "nextCursor": "opaque-cursor" },
  "meta": { "requestId": "request-id" }
}
```

นี่คือตัวอย่าง response แบบย่อเพื่ออธิบาย envelope ไม่ใช่รายการฟิลด์ PO ทั้งหมด

| รูปแบบ | วิธีใช้ |
|---|---|
| Document list เช่น PO/carrier/goods/issue/report | `limit` 1–100, default 20; ส่ง `nextCursor` ต่อใน `cursor`; ไม่มี total สำหรับกระโดดเลขหน้า |
| Catalog/inventory/balance/ledger แบบมี `page` | page เริ่ม 1, limit 1–100, default 20; มี total และเลขหน้า |
| Lookup | สูงสุด 50; ไม่มี page metadata |
| Detail/mutation | `{ data, meta }` |

เมื่อเปลี่ยน search/filter ให้ทิ้ง cursor และรายการสะสมเดิม โหลดหน้าแรกใหม่ เมื่อโหลดเพิ่มให้คง filter ทุกตัวรวมถึง `false` และ deduplicate ตาม ID

Boolean ใหม่รับเฉพาะข้อความ `true`/`false`; ห้ามส่ง `1`, `0`, `TRUE` หรือค่าว่าง ID ต้องเป็น integer บวกไม่เกิน 2147483647

ใช้ `apiGet`/`apiPost` จาก `lib/api/client.ts` ต่อ ตัว transport มี session credentials, JSON/error handling, request ID, GET timeout 20 วินาที และรองรับ AbortSignal แล้ว

## 4. แผนแก้ FE แยกตามไฟล์

### 4.1 `lib/api/warehouse.ts` — ทำ wrapper ให้เลือก use case ได้

คง wrapper full เดิมสำหรับหน้ารายละเอียด เพิ่ม options หรือ wrapper แยกสำหรับ selector/compact โดยตรวจ call sites เดิมก่อนเปลี่ยน signature

| Wrapper ที่เสนอให้เพิ่ม/ขยาย | พารามิเตอร์ที่ต้องรองรับ |
|---|---|
| PO page สำหรับ selector | `cursor`, `limit`, `q`, `closed`, `signal` |
| Carrier page สำหรับ selector | `cursor`, `limit`, `received`, `hasGoodsReceipt`, `signal` |
| `purchaseOrderLines` | `id`, `signal`; ส่ง `view=lines` |
| `carrierConfirmation` | `id`, `signal`; ส่ง `view=confirmation` |
| `catalogLookup` | `kind`, `q`, `branchId` สำหรับ warehouses, `signal`; ไม่ใส่ page |
| Warehouse paginated selector | ส่ง `branchId` กับ catalogPage เดิมเพื่อโหลดรายการให้ครบ |

ขณะนี้ `purchaseOrdersPage` รองรับ cursor/signal/q แต่ยังไม่ส่ง `closed`; `carrierReceiptsPage` ยังไม่รับ filters ใหม่; `catalog(kind, signal)` ยังเรียก legacy list

ตัวอย่างการประกอบ query สำหรับ selector ที่ FE นำไปใส่ใน wrapper ได้:

```ts
const params = new URLSearchParams({ limit: "20" });
if (cursor) params.set("cursor", cursor);
if (query.trim()) params.set("q", query.trim());
if (closed !== undefined) params.set("closed", String(closed));

const response = await apiGet<PurchaseOrder[]>(
  `/api/purchase-orders?${params}`,
  { signal },
);
// อ่าน response.data และ response.page ตาม cursorPage helper เดิม
```

ตัวอย่างนี้เป็น fragment สำหรับ wrapper ไม่ใช่โค้ดที่ถูกเพิ่มแล้ว `closed` เป็น `boolean | undefined`; อย่าใช้ `if (closed)` เพราะจะทำให้ false หายไป

แยก type ของ full/compact ตาม fields จริง โดยเฉพาะ PO line สำหรับ EMPLOYEE ไม่ใช้ type assertion ทำให้ฟิลด์ที่ไม่ได้ส่งดูเหมือนมีอยู่

### 4.2 `ReceiveScreen.tsx` และ `ReceiveSupplier.tsx`

1. รักษารายการประวัติและ selector เป็นคนละ resource/filter แม้เรียก endpoint เดียวกัน
2. Supplier selector/search ใช้ `closed=false`; เมื่อเลือก PO ให้ `SupplierForm` เรียก `view=lines`
3. ถ้าข้อมูล PO full ที่ parent มีตรง ID และยังใช้ได้ สามารถใช้ lines ของข้อมูลนั้นแทนคำขอใหม่ แต่ต้องไม่ใช้ stale quantity หลัง mutation
4. CarrierForm ค้น PO ที่เปิดอยู่ด้วย `closed=false`; ส่ง `purchaseOrderCode` ตาม body เดิม
5. Full PO/carrier detail ที่ parent เปิดจากรายการคง full view เพื่อไม่กระทบ `PoDetails`/`CarrierDetails`
6. ห้ามให้ effect จากการเลือก detail ที่ยังค้างในแท็บเก่ายิงคำขอที่ไม่ใช้ในแท็บใหม่; ตรวจ active step และ abort/ignore ผลเก่า

ฟอร์ม Receive ปัจจุบันแสดงทันทีเมื่อเปิดแท็บ จึงมีเหตุผลที่ต้องโหลด reference ในแท็บนั้น หากเปลี่ยนเป็นฟอร์มเปิดตามปุ่ม ค่อยตั้ง `enabled` ให้สัมพันธ์กับสถานะเปิดฟอร์ม อย่าหยุดโหลด reference ทั้งที่ฟอร์มยังแสดงและต้องใช้

### 4.3 `ReceiveCount.tsx` — flow หลักที่ควรปรับก่อน

ลำดับที่แนะนำ:

1. เข้าแท็บนับ: โหลด goods receipts สำหรับรายการ และ carrier selector ด้วย `received=true&hasGoodsReceipt=false`
2. ยังไม่เลือก carrier: ไม่โหลด PO detail หรือคลังทั้งหมด
3. เลือก carrier: โหลด `/api/carrier-receipts/{id}?view=confirmation`
4. ใช้ `purchase_order_id` โหลด PO `view=lines`; ใช้ `confirmation.receiving_branch_id` โหลด warehouses ตาม `branchId` ทั้งสองคำขอนี้ทำขนานได้หลังได้ carrier
5. แสดงเฉพาะคลัง active ตามเงื่อนไขฟอร์มเดิม และรองรับค้นหา/โหลดเพิ่มถ้าใช้ lookup
6. ถ้า `confirmation` เป็น null ให้แจ้งว่าต้องยืนยันรับก่อน ไม่เปิดให้บันทึกผลนับ
7. เปลี่ยน carrier หรือ branch: abort คำขอเก่าและรีเซ็ต carrier/PO/warehouseId/count ที่ผูกกับเอกสารเก่า เพื่อไม่ให้เลือกคลังหรือจำนวนของรายการก่อนหน้า
8. Mutation ยังใช้ `createGoodsReceipt` และ `postGoodsReceipt` ตามขั้นตอนเดิม บันทึกผลนับยังไม่เท่ากับลงสต๊อก

Flow ใหม่อาจลดคำขอช่วงเข้าแท็บจาก 3 เป็น 2 ด้วยการเลื่อน warehouse request ไปหลังเลือก carrier แต่เมื่อเลือกแล้วจะมีคำขอคลังเพิ่ม จึงไม่ได้รับประกันว่าจำนวน HTTP ตลอด flow จะลดลง ประโยชน์ที่แน่นอนคือโหลดคลังเฉพาะสาขาและไม่ใช้ full detail กับฟอร์มนับ

### 4.4 `CatalogScreen.tsx` และ `ProductInventorySplitView.tsx`

- ตาราง catalog และ inventory คง paginated API เดิม; lookup ใช้กับ selector ไม่แทนตารางเต็ม
- `CatalogScreen.loadRefs` โหลดตาม `requiredRefs` เมื่อเปิดฟอร์มอยู่แล้ว ให้คงการโหลดเฉพาะ reference ที่ใช้งาน
- Product inventory มี categories/warehouses สำหรับ filter และ units/brands สำหรับ modal แยกกันแล้ว ใช้ lookup ได้เมื่อ UI ค้นหา/เข้าถึงตัวเลือกนอก 50 แรกได้
- Warehouse form/selector เมื่อมีสาขาที่เลือก ให้ส่ง `branchId` ไป BE แทนการดึงทุกคลังมา filter
- ไม่เพิ่ม groupId/brandId filter API ที่ BE รอบนี้ยังไม่ได้ทำ การใช้ parent fields ใน lookup เป็นข้อมูลสำหรับ FE ไม่ได้หมายถึงมี query parameter ใหม่
- โหลด reference ขนานเฉพาะชุดที่จำเป็น และอย่า refresh reference ทั้งชุดหลังแก้ข้อมูลที่ไม่เกี่ยวกับ catalog

### 4.5 `StockScreen.tsx` และหน้าที่ใช้ร่วมกัน

`/warehouse/stock` และ `/warehouse/transfer` ใช้ `StockScreen` เดียวกัน; `/warehouse/movements` ใช้ตัวเดียวกันโดยเปิด ledger เป็นค่าเริ่มต้น จึงตรวจทุก entry point เมื่อเปลี่ยน component นี้

- balances/ledger โหลดเฉพาะแท็บ active อยู่แล้ว รักษาการแบ่งหน้าและ filter เดิม
- Warehouse catalog ถูกใช้กับ filter ที่แสดงทันทีด้วย จึงไม่ควรเลื่อนการโหลดทั้งหมดไปจนเปิด movement form
- ใช้ lookup/search หรือ paginated selector เพื่อลด payload โดยคงการเลือกคลังนอก 50 แรกได้
- ทำ action สร้าง/reverse แล้ว refresh balances หรือ ledger ที่กำลังแสดง ไม่เรียก overview/receive/reports/catalog ทั้งหมด
- แยก loading ของ action ออกจากตารางเดิม ป้องกัน submit ซ้ำ และแสดง error โดยคงข้อมูลที่ผู้ใช้กรอก
- `/warehouse/transfer/audit` ปัจจุบัน redirect ไป `/warehouse/issues` ไม่ใช่ transfer audit API/approval flow ใหม่ อย่าออกแบบการเชื่อมต่อโดยสมมติว่ามี backend ชุดนั้น

### 4.6 Hooks, การโหลดซ้ำ และบัญชี

`hooks/useRemoteResource.ts` (`useRemote`) abort และกันผลเก่าทับผลใหม่แล้ว แต่ไม่ได้ cache ข้ามหน้า; เมื่อ callback `load` เปลี่ยน identity จะ refresh ผ่าน effect

- ใช้ `useCallback` ผูก dependencies กับ account scope, resource, view, search/filter และ page ที่ต้องใช้จริง
- อย่าให้ input ของฟอร์มที่ไม่เกี่ยวกับรายการไปเปลี่ยน callback ของ list loader
- ใช้ context บัญชีเดิม; การรวม pending `/api/me` ไม่ใช่ cache ถาวร
- ใช้ `useCursorResource` หรือรูปแบบ cursor ที่มีอยู่ได้ แต่ต้องคง query/filter เดียวกันในทุกหน้า
- ถ้าจำเป็นต้องใช้ cache/dedup สำหรับ lookup ให้เริ่มจากกลไกใน FE ที่มีอยู่ ไม่ต้องเพิ่ม package เพื่อทำรอบนี้
- Key ต้องแยก catalog kind, q, branchId, account scope และสำหรับ detail ต้องแยก id/view; clear เมื่อ logout/เปลี่ยนบัญชีหรือสิทธิ์
- แยก pending request กับการเก็บผล ห้าม abort งานร่วมจาก consumer หนึ่งจน consumer อื่นเสียงาน; ใช้ loader เจ้าของเดียวหรือออกแบบ cancellation ให้ชัด
- Abort request ไม่ได้แปลว่า query ที่ BE เริ่มแล้วหยุดทันที การลดคำขอไม่จำเป็นต้องทำตั้งแต่ก่อนเริ่ม fetch

## 5. Refresh หลัง mutation ให้สัมพันธ์กับข้อมูลที่เปลี่ยน

| Action | รายการ/detail ที่ควรทำให้สด | Reference ที่ปกติไม่ต้องโหลดใหม่ |
|---|---|---|
| สร้าง/แก้/ปิด PO | PO list/selector ที่แสดง และ PO full/lines ของ ID นั้นที่ใช้งาน | suppliers, branches, warehouses, CEOs |
| สร้าง supplier receipt | supplier list ที่แสดง และ PO detail/lines ที่เกี่ยวข้อง | catalog ทั้งชุด |
| สร้าง carrier receipt | carrier list ที่แสดง; PO detail/จำนวน carrier ที่เกี่ยวข้อง | catalog ทั้งชุด |
| ยืนยันรับ carrier | carrier list/detail/confirmation และ selector สำหรับนับที่ใช้งาน | catalog; ถ้า branch เปลี่ยน ให้โหลด warehouse selector สำหรับ branch ใหม่ |
| สร้าง goods receipt | goods list, carrier eligibility (นำเอกสารที่นับแล้วออก), PO quantities ที่ใช้งาน | catalog ทั้งชุด |
| Post goods receipt | goods list/detail, PO quantities และ stock data ที่กำลังแสดง | catalog ทั้งชุด |
| สร้าง/reverse stock document | balances/ledger ที่แสดง; ถ้า reversal เกี่ยวกับ goods receipt ให้ invalidate receipt/PO ที่เกี่ยวข้องเมื่อมี cache | catalog ทั้งชุด |
| สร้าง/แก้ catalog | ตาราง kind นั้น และ lookup cache/reference ของ kind ที่เปลี่ยน | catalog kind อื่นที่ไม่ได้รับผล |

ตารางนี้ใช้เป็นรายการ dependency ไม่ได้สั่งให้ fetch ทุกหน้าในทันที Resource ที่ไม่ได้แสดงให้ invalidate แล้วโหลดเมื่อเปิดใช้งานต่อไป

## 6. Stock write API และ idempotency

### สร้างเอกสาร

```http
POST /api/stock/documents
Content-Type: application/json
Idempotency-Key: movement-key-123
```

```json
{
  "kind": "ISSUE",
  "warehouseId": 7,
  "reason": "เบิกใช้ภายใน",
  "lines": [{ "productId": 3, "quantity": "2", "serialNumbers": [] }]
}
```

- `ISSUE`/`TRANSFER` ใช้ `quantity` บวก; `TRANSFER` เพิ่ม `destinationWarehouseId`
- `ADJUSTMENT` ใช้ `quantityDelta` ที่ไม่ใช่ศูนย์ รับค่าบวก/ลบตาม service เดิม
- key ต้องยาว 8–120 ใช้ตัวอักษร ตัวเลข `_` หรือ `-`; `crypto.randomUUID()` ใช้ได้
- ผลสำเร็จ HTTP 201: `data` มี `inventoryDocumentId`, `destinationDocumentId` (nullable), `repeated: false`
- Replay key เดิมกับข้อมูลเดิม: `inventoryDocumentId`, `repeated: true`; ไม่รับประกันว่ามี `destinationDocumentId` ใน replay
- Key เดิมแต่ข้อมูลเปลี่ยนได้ 409 `IDEMPOTENCY_CONFLICT`
- ใช้ได้สำหรับ ADMIN/CEO/MANAGER และ warehouse branch ที่มีสิทธิ์; BE ตรวจ active warehouse/product, quantity, serial, transaction และ ledger ตามเดิม

`warehouseApi.createStockDocument()` ปัจจุบันสร้าง key ใหม่ทุกครั้งที่เรียก ถ้า FE ทำ retry หลัง network error ต้องเก็บ key เดิมสำหรับ submit เดิมและ body เดิม ไม่สร้าง key ใหม่เพราะยังไม่รู้ว่า request ก่อนหน้าเขียนสำเร็จหรือไม่ เมื่อเริ่มรายการใหม่จึงใช้ key ใหม่ อย่า retry mutation อัตโนมัติโดยไม่มีการจัดการนี้

### กลับรายการ

```http
POST /api/stock/documents/12/reverse
Content-Type: application/json
```

```json
{ "reason": "แก้ไขการบันทึกผิด" }
```

สำเร็จ HTTP 200: `data: { reversalDocumentIds: [13] }`; transfer pair อาจมีหลาย ID ไม่ต้องส่ง Idempotency-Key ให้ route นี้ การกลับซ้ำมี conflict check เดิม ใช้ `document_id` จาก ledger ไม่ใช่ movement row `id`

Wrapper stock/reverse มีอยู่ใน FE แล้ว ให้ตรวจ flow ด้วย routes ที่ BE เพิ่ม ไม่ต้องสร้าง endpoint ชื่ออื่น

## 7. การจัดเมนู ถ้าจะทำต่อ

ข้อเสนอด้าน navigation แยกจากงานเชื่อม API รอบนี้:

| กลุ่มที่เสนอ | เมนู/หน้าที่นำมารวม |
|---|---|
| ภาพรวม | ภาพรวมคลัง |
| รับสินค้า | PO, เอกสารผู้ขาย, เอกสารขนส่ง/รับของ, นับ/ลงสต๊อก เป็นขั้นตอนใน Receive |
| สต๊อกและการเคลื่อนไหว | ยอดคงเหลือ, จ่าย/ปรับ/โอน, ledger |
| ข้อมูลหลัก | สินค้า, สาขา, คลัง, ผู้ขาย, หน่วย, กลุ่ม, หมวด, ยี่ห้อ, รุ่น |
| ปัญหาและรายงาน | issues, reports |

การจัดกลุ่มนี้ยังไม่ได้ implement และไม่ต้องรอจัดเมนูจึงเริ่มใช้ API ใหม่ได้ คง URL/สิทธิ์เดิมเมื่อจัด navigation อย่า mount ทุก screen หรือ preload domain data ทุกเมนูในกลุ่มเพียงเพราะเปิด accordion

- [ ] Parent detail ของ PO/carrier คง full; ไม่มี compact data เขียนทับ full
- [ ] Catalog selector รองรับค้นหา/โหลดเพิ่มและรักษาค่าที่เลือก ก่อนเปลี่ยนไปใช้ lookup 50
- [ ] ปรับ refresh/invalidation ตาม resource ที่เปลี่ยน; ใช้ account context เดิม
- [ ] ตรวจ stock create/reverse และเก็บ idempotency key เดิมสำหรับ retry รายการเดิม
- [ ] วัด Network ก่อน/หลัง; ทำ menu regroup เป็นงานแยกถ้าต้องการ

### Acceptance checks

- เข้าแต่ละแท็บแล้วไม่มี list API ของแท็บที่ไม่ได้ใช้; reference มีเหตุผลตาม filter/ฟอร์มที่แสดง
- Supplier/count form ส่ง compact URL จริง; full detail ยังมีหลักฐานและสถานะเอกสารผูกตามเดิม
- PO ที่ยังเปิดและ carrier ที่เลือกนับได้ซึ่งอยู่เลยหน้าแรกสามารถค้นหา/โหลดเพิ่มเจอ
- คำขอ cursor ถัดไปยังมี closed/received/hasGoodsReceipt เดิม; เปลี่ยน filter แล้วเริ่มหน้าแรกใหม่
- Lookup ที่มีข้อมูลเกิน 50 ไม่ทำข้อมูลนอกชุดแรกเลือกไม่ได้ และค่าเดิมไม่หายเมื่อผลค้นหาเปลี่ยน
- รับ carrier A แล้วเลือก B อย่างรวดเร็ว ผล A ไม่ทับ B; ล้าง warehouseId/count ของ A และเลือกได้เฉพาะคลังสาขารับของ B
- ทดสอบ scope ของ MANAGER/COUNTER_STAFF และ catalog restriction ของ EMPLOYEE; ไม่อนุมานสิทธิ์จากการซ่อนเมนู
- สร้าง goods receipt แล้วยังไม่เพิ่ม stock; post เพิ่มเฉพาะของดีตามเดิม; damaged/wrong ยังใช้ issue/evidence requirements เดิม
- Error 400 แสดง validation, 401/403 แสดงสถานะบัญชี/สิทธิ์, 404 แสดงไม่พบ, 409 แสดง conflict พร้อมรักษาฟอร์ม
- Loading ใหม่ใช้ SkeletonBox สำหรับเนื้อหา และ Loader2 สำหรับ action ตาม AGENTS.md ไม่เพิ่ม plain text loading ใน JSX
- Typecheck/lint/build และตรวจ flow ด้วยข้อมูลทดสอบจริงตามสิทธิ์ที่อนุญาต

### วิธีวัดว่าลดโหลดจริงหรือไม่

เปิด DevTools Network เลือก Fetch/XHR เริ่มจากหน้าที่ต้องการและ clear log ก่อนทำ flow เดียวกัน เทียบ URL รวม query string, จำนวนคำขอ, transferred bytes และระยะเวลาของแต่ละ action แยกเข้าแท็บ/เลือกเอกสาร/บันทึก/refresh

แยก dev-mode remount หรือ aborted requests ออกจากคำขอสำเร็จ แต่ตรวจด้วยว่าคำขอที่ถูก abort เริ่มงานไปแล้วหรือไม่ เก็บ `x-request-id`/`meta.requestId` และ `Server-Timing` เพื่อเทียบกับ BE เมื่อจำเป็น ไม่สรุปจาก terminal log สะสมข้ามหน้าหรือจากชื่อ path ที่ไม่มี query string
