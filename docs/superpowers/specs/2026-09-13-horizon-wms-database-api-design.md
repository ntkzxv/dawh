## 1. Objective

เอกสารนี้แปลง product scope ใน `DESIGN.md` ให้เป็น database blueprint และ HTTP API contract สำหรับ Horizon WMS โดยครอบคลุม Identity, Authorization, Warehouse, Product, Inventory, Receiving, Putaway, Movement, Adjustment, Stock Count, Transfer, Picking, Packing, Shipment, Destination Receiving, Claim, Notification, Report และ Audit

เอกสารนี้ยังไม่ใช่ executable migration หรือ OpenAPI YAML จุดประสงค์คือให้ทีมอนุมัติ model, boundary และ contract ก่อนสร้าง implementation plan, migrations และ route handlers

## 2. Confirmed Architecture

```text
Browser / PWA
    |
    | HTTPS JSON/CSV/PDF
    v
Next.js 16 Route Handlers (/api/v1)
    |
    +-- Better Auth session validation
    +-- Permission and facility-scope authorization
    +-- Schema validation
    +-- Idempotency and optimistic concurrency
    v
Application services
    |
    +-- short PostgreSQL transactions
    +-- deterministic stock locking order
    +-- audit + outbox in the same transaction
    v
Repository / DAL
    |
    v
Supabase PostgreSQL (private schemas)
```

### 2.1 Schemas

| Schema | Responsibility | Data API exposure |
|---|---|---|
| `better_auth` | Better Auth managed tables | No |
| `app` | All WMS business and operational tables | No |
| `public` | No business tables; extensions only when required | Default access revoked |

The application uses two server-only database clients:

- Auth client: `search_path=better_auth`, owned and migrated by Better Auth.
- WMS client: `search_path=app,public`, connected with a least-privilege login role.

For serverless deployment, use the Supabase transaction pooler, SSL required, application pool size `1`, and prepared statements disabled. Migrations use a direct or session connection, not transaction pooling.

### 2.2 Chosen Data Strategy

The design uses a normalized transactional model with an append-only inventory ledger and a mutable balance projection.

- `inventory_transactions` and `inventory_transaction_lines` are the audit source of truth for stock.
- `stock_balances` is the current-state projection optimized for reads and locking.
- Operational documents use normalized header/item tables.
- State transitions are explicit service commands, never arbitrary status updates.
- JSONB is limited to snapshots, non-queryable metadata, audit differences, and report parameters.

Rejected alternatives:

- Full event sourcing: strong history, but replay, projection recovery, and developer overhead are excessive for a two-person MVP.
- JSONB-first document storage: fast to prototype, but weak for constraints, joins, stock locking, reporting, and schema evolution.

## 3. Global Database Conventions

### 3.1 Naming and Types

- Identifiers use `snake_case`; table names are plural.
- Internal primary keys are application-generated UUIDv7 stored as `uuid`.
- Human document numbers are separate immutable `text` values, for example `TRF-202609-0001`.
- Timestamps are `timestamptz` in UTC.
- Quantities are `numeric(18,6)` in the product base unit.
- Currency values are `numeric(18,2)` plus `currency_code char(3)` where applicable.
- Weights and dimensions are `numeric(18,6)` with a documented canonical unit.
- Free-form strings use `text`; business limits are enforced with `check` constraints.
- Status and type values use `text` with named `check` constraints. PostgreSQL enum types are avoided to keep migrations easier.
- Every foreign key used for joins or cascades receives an index.
- Every externally visible mutable resource has an integer `version` for optimistic concurrency.

### 3.2 Shared Columns

Most mutable master and document tables include:

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key; UUIDv7 generated by the application |
| `created_at` | `timestamptz` | Not null; database default `now()` |
| `created_by` | `text` | Better Auth user ID; not null for user actions |
| `updated_at` | `timestamptz` | Not null; updated by application |
| `updated_by` | `text` | Better Auth user ID |
| `version` | `integer` | Starts at 1; increments on accepted mutation |

Master data that can be retired uses `is_active boolean`, not hard delete. Posted operational documents use status transitions, reversal, or cancellation and cannot be deleted.

### 3.3 Organization Model

The MVP has one organization, but `organization_id` remains in tenant-root tables to prevent a future destructive migration. It is not accepted from the browser; the request context supplies it.

### 3.4 Integrity Rules

- All quantities are non-negative except ledger deltas.
- Source and destination facilities or locations must differ for movement documents.
- Product tracking method determines whether lot or serial is required.
- A serial-tracked item can have only one positive balance row in the entire network.
- A posted ledger transaction is immutable and cannot be deleted.
- A stock operation locks affected balance rows in ascending `(product_id, lot_id, serial_id, location_id, stock_status)` order.
- Negative stock is rejected by database constraint and service precondition.
- External calls and file uploads never execute while stock rows are locked.
- Audit log, notification outbox, ledger, balance, and document-state updates commit atomically.

- `facilities (organization_id, facility_type, is_active)`
- `facility_routes (destination_facility_id, source_facility_id)`
- `warehouse_locations (facility_id, parent_id)`

## 7. Inventory Core

### 7.1 `app.stock_balances`

Current quantity at one inventory grain.

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key |
| `facility_id` | `uuid` | Not null |
| `location_id` | `uuid` | Required for physical stock; null for shipment custody |
| `product_id` | `uuid` | Not null |
| `lot_id` | `uuid` | Nullable according to tracking method |
| `serial_id` | `uuid` | Nullable according to tracking method |
| `shipment_id` | `uuid` | Required only for `IN_TRANSIT` or shipment-linked `LOST` stock |
| `stock_status` | `text` | `AVAILABLE`, `RESERVED`, `PICKED`, `PACKED`, `IN_TRANSIT`, `QUARANTINE`, `DAMAGED`, `CLAIM_PENDING`, `EXPIRED`, `LOST` |
| `quantity` | `numeric(18,6)` | Not null and `>= 0` |
| `version` | `bigint` | Incremented on every stock mutation |
| `updated_at` | `timestamptz` | Not null |

Use a unique index with `NULLS NOT DISTINCT` on `(facility_id, location_id, shipment_id, product_id, lot_id, serial_id, stock_status)`. Physical stock requires `location_id` and forbids `shipment_id`; transit stock requires `shipment_id` and has no physical `location_id`. The application verifies that transit custody uses the shipment source facility. Add a partial unique index on `serial_id` where `serial_id is not null and quantity > 0`.

Derived quantities use mutually exclusive stock buckets:

```text
Physical On-hand = AVAILABLE + RESERVED + PICKED + PACKED + QUARANTINE
                 + DAMAGED + CLAIM_PENDING + EXPIRED
Available = AVAILABLE
Available-to-Transfer = max(AVAILABLE - Safety Stock, 0)
Network In-transit = IN_TRANSIT grouped through shipment source/destination
```

### 7.2 Ledger Tables

#### `app.inventory_transactions`

Immutable operation header.

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key |
| `transaction_no` | `text` | Unique, immutable |
| `organization_id` | `uuid` | Not null |
| `transaction_type` | `text` | `RECEIVE`, `PUTAWAY`, `MOVE`, `RESERVE`, `RELEASE_RESERVATION`, `PICK`, `PACK`, `DISPATCH`, `RECEIVE_TRANSFER`, `QUARANTINE`, `CLAIM_HOLD`, `ADJUST`, `WRITE_OFF`, `RETURN`, `REVERSE` |
| `reference_type` | `text` | Controlled document type |
| `reference_id` | `uuid` | Referenced document ID |
| `reversal_of_id` | `uuid` | Nullable FK to original transaction |
| `reason_code_id` | `uuid` | Nullable |
| `note` | `text` | Nullable |
| `occurred_at` | `timestamptz` | Business time |
| `posted_at` | `timestamptz` | Database posting time |
| `posted_by` | `text` | Better Auth user ID |
| `idempotency_key_id` | `uuid` | Unique when supplied |

#### `app.inventory_transaction_lines`

Immutable balance delta lines.

| Column | Type | Rule |
|---|---|---|
| `id` | `uuid` | Primary key |
| `transaction_id` | `uuid` | FK; not null |
| `line_no` | `integer` | Unique per transaction |
| `facility_id`, `product_id` | `uuid` | Not null |
| `location_id`, `shipment_id` | `uuid` | Physical or shipment custody grain |
| `lot_id`, `serial_id` | `uuid` | Nullable by tracking method |
| `stock_status` | `text` | Target balance bucket |
| `quantity_before` | `numeric(18,6)` | Not null |
| `quantity_delta` | `numeric(18,6)` | Non-zero |
| `quantity_after` | `numeric(18,6)` | Must equal before + delta and be non-negative |
| `posted_at` | `timestamptz` | Copied from immutable header for ledger keyset queries |

Indexes:

- `inventory_transactions (reference_type, reference_id, posted_at desc)`
- `inventory_transactions (organization_id, posted_at desc, id desc)`
- `inventory_transaction_lines (product_id, facility_id, posted_at desc, id desc)`
- `inventory_transaction_lines (location_id, product_id, lot_id, serial_id)`

Each transaction may contain at most one line for the same balance grain. This makes `quantity_before` and `quantity_after` unambiguous.

### 7.3 Reservation Tables

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `stock_reservations` | Reservation header | `reservation_no`, `transfer_id`, `facility_id`, `status`, `expires_at`, `released_at`; one active reservation per transfer allocation |
| `stock_reservation_lines` | Reserved inventory grain | `reservation_id`, `transfer_item_id`, `location_id`, `product_id`, `lot_id`, `serial_id`, `quantity_reserved`, `quantity_consumed`, `quantity_released` |

Reservation creation moves quantity from `AVAILABLE` to `RESERVED` through the ledger. Consumption and release are explicit ledger operations.

### 7.4 Stock Mutation Algorithm

Every stock-changing command follows this sequence:

1. Validate session, permission, scope, input, and document state outside the transaction where possible.
2. Start a short database transaction.
3. Claim the idempotency key or return the stored response.
4. Lock every affected `stock_balances` row in deterministic order using `FOR UPDATE`.
5. Re-check available quantity, safety stock, serial uniqueness, document version, and state.
6. Insert immutable transaction header and lines.
7. Upsert balances and increment balance versions.
8. Update document status/version and insert workflow history.
9. Insert audit log and outbox events.
10. Commit, then perform delivery of notifications or file operations asynchronously.

## 10. Shipment and Destination Receiving Tables

### 10.1 Shipment

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `shipments` | Dispatch and delivery header | `shipment_no`, transfer, source/destination, `status`, `exception_status`, carrier, driver, phone, vehicle registration, tracking number, seal, expected/actual departure and delivery timestamps |
| `shipment_packages` | Shipment-package mapping | shipment/package unique pair; a dispatched package belongs to one active shipment |
| `shipment_events` | Append-only timeline | shipment, event type, event time, facility/location text, coordinates, note, actor, source |
| `proofs_of_delivery` | POD record | shipment, receiver name, method, OTP verification result, received package count, signature/image object keys, confirmed by/at |

Shipment states: `DRAFT -> READY -> DISPATCHED -> IN_TRANSIT -> ARRIVED -> DELIVERED -> RECEIVED -> COMPLETED`; `CANCELLED` is an exit before dispatch. Delay, delivery failure, damage/loss, and claim status live in `exception_status` and append-only events rather than replacing the core state.

Dispatch is one idempotent stock transaction: source `RESERVED`/`PACKED` decreases and network `IN_TRANSIT` increases. Destination on-hand remains unchanged.

### 10.2 Destination Receipt

| Table | Purpose | Important columns / constraints |
|---|---|---|
| `destination_receipts` | Destination inspection | `receipt_no`, shipment, destination facility, status, started/confirmed metadata, package counts |
| `destination_receipt_packages` | Package inspection | receipt/package, seal result, package condition, received flag, note |
| `destination_receipt_items` | SKU inspection result | receipt, shipment/package/product/lot/serial, expected quantity, accepted quantity, exception quantity, result code, destination location |

States: `DRAFT -> IN_PROGRESS -> CONFIRMED -> COMPLETED`; final result can be `COMPLETED_WITH_EXCEPTION`.

Confirmation consumes `IN_TRANSIT` and creates destination `AVAILABLE`, `QUARANTINE`, or `CLAIM_PENDING` balances in one transaction. The total destination deltas must equal the in-transit decrease for each product/lot/serial.

## 14. API Conventions

### 14.1 Base Contract

- Base path: `/api/v1`
- Media type: `application/json; charset=utf-8`
- Dates: RFC 3339 UTC strings
- Quantities and money: decimal strings in JSON to avoid floating-point loss
- IDs: UUID strings; document numbers are separate fields
- Language: response codes and field names are English; UI translates messages
- Authentication: Better Auth secure session cookie
- CSRF: Better Auth protection plus same-origin checks for cookie-authenticated mutations
- Request tracing: every response includes `X-Request-Id`
- Mutation deduplication: `Idempotency-Key` required on stock-posting and externally retryable commands
- Concurrency: mutable document commands require `If-Match: "<version>"`

Single resource:

```json

  "data": {

    "version": 3
  },
  "meta": {
    "requestId": "req_01K4Z6T9J4X"
  }
```

Collection:

```json
{
  "data": [],
  "page": {
    "limit": 50,
    "nextCursor": null,
    "hasMore": false
```

### 17.3 Idempotency Behavior

- The same key and same request hash returns the original status code and response body.
- The same key with a different request hash returns `409 IDEMPOTENCY_KEY_REUSED`.
- An in-progress duplicate waits briefly or returns `409 OPERATION_IN_PROGRESS` with a retry hint.
- Keys for stock mutations are retained for at least 72 hours; document-number side effects are never recreated.

## 18. State and Concurrency Enforcement

- Clients never send a new `status` through generic `PATCH`.
- Every state change has an explicit command endpoint and transition allowlist.
- Commands compare `If-Match` against the document `version` inside the transaction.
- Stock availability is recalculated after row locks, not trusted from a preflight response.
- Approval endpoints record an immutable decision snapshot.
- Posted documents cannot be edited. Corrections use reversal/adjustment commands.
- Deadlock retries are limited, jittered, and only used for idempotent commands.

## 19. Security Design

- Business schemas are not exposed through Supabase Data API.
- `anon` and `authenticated` Supabase roles receive no privileges on `app` or `better_auth`.
- Browser bundles contain no database password, service-role key, or storage secret.
- The WMS database login is not a superuser and receives only required schema/table/function privileges.
- Route authorization checks both permission and facility scope for every resource.
- Out-of-scope records normally return `404` to reduce identifier disclosure.
- Better Auth user metadata is not treated as authorization truth; roles/scopes live in `app` tables.
- Sensitive values are redacted from logs and audit JSON.
- Evidence downloads use short-lived signed URLs after entity authorization.
- File completion verifies expected bucket, key, MIME type, size, and checksum.
- Rate limits apply to auth, scans, signed URLs, exports, and high-impact commands.
- Database RLS is not the primary authorization mechanism because Better Auth context is application-owned and the schema is private. Least privilege is mandatory; transaction-scoped RLS using `SET LOCAL` may be added later only with integration tests and without relying on pooled session state.

## 20. Index Plan

Every FK receives an index. In addition, initial composite/partial indexes should match the main access paths:

- Active task queues: `(facility_id, status, priority desc, created_at, id)` with a partial predicate for open statuses.
- Transfer queues: `(destination_facility_id, status, required_date, id)` and `(source_facility_id, status, created_at, id)`.
- Shipment monitoring: `(destination_facility_id, status, expected_delivery_at, id)` with a partial predicate for active shipments.
- Claim SLA: `(status, response_due_at, id)` and `(status, investigation_due_at, id)` for open claims.
- Notifications: `(recipient_user_id, read_at, created_at desc, id desc)` with a partial unread index.
- Audit: `(organization_id, occurred_at desc, id desc)`, `(entity_type, entity_id, occurred_at desc)`, and `(actor_user_id, occurred_at desc)`.
- Product lookup: unique SKU and barcode indexes plus trigram indexes only after search requirements are measured.
- Expiry: `(expiry_date, product_id)` for active lots with non-zero stock joined through balances.

Index definitions will be finalized against repository queries and verified with `EXPLAIN (ANALYZE, BUFFERS)` during implementation. Avoid speculative single-column indexes that duplicate composite prefixes.

## 22. Reporting Read Model Strategy

MVP reports query normalized tables with purpose-built indexes. Use SQL views only when they reduce repeated query logic; every view in an exposed schema must be `security_invoker`, but this design keeps report views private in `app`.

Materialized views or summary tables are introduced only when measured dashboard latency exceeds the target. Initial targets:

- List/read API p95 under 500 ms at MVP volume.
- Stock mutation p95 under 1 second excluding file upload.
- Organization dashboard p95 under 2 seconds.
- Large CSV/PDF exports handled asynchronously.

## 23. Deletion and Retention

- Master records referenced by operations are deactivated, not deleted.
- Draft documents may be cancelled; hard delete is reserved for never-posted test data through admin tooling outside the public API.
- Ledger, audit, workflow history, shipment events, and claim history are immutable.
- Idempotency response bodies expire after the retention window, but key identity and operation reference may be retained longer.
- Storage objects are deleted only when no attachment/evidence row references them and retention policy permits deletion.
- Exact legal retention periods require business approval before production launch.

## 24. Testing Requirements

### 24.1 Database Contract Tests

- Reject negative balance and invalid quantity arithmetic.
- Enforce unique balance grain with null lot/serial values.
- Prevent a serial from having two positive balance rows.
- Reject cross-facility location relationships.
- Verify every FK has a supporting index.
- Verify immutable ledger/audit tables reject update/delete for the application role.

### 24.2 Transaction Integration Tests

- Concurrent allocations cannot reserve more than available stock.
- Safety stock is rechecked after lock acquisition.
- Dispatch decreases source and increases in-transit exactly once.
- Partial receipt consumes all transit and creates accepted plus exception buckets.
- Adjustment requires a different requester and approver.
- Claim resolution creates the correct compensating ledger entries.
- Idempotent replay returns the original response without new ledger rows.
- Opposite-direction multi-row movements do not deadlock under deterministic locks.

### 24.3 API Contract Tests

- Unauthenticated calls return `401` with the standard error envelope.
- Out-of-scope facility IDs return `404`/`FORBIDDEN_FACILITY_SCOPE` according to disclosure policy.
- Invalid state commands return `409 INVALID_DOCUMENT_STATE`.
- Missing/stale `If-Match` returns `409 VERSION_CONFLICT`.
- Mutation payloads reject unknown fields where strict schemas are used.
- Cursor pagination has no duplicates or gaps for a stable snapshot ordering.
- File routes reject spoofed object keys and unsupported content.

### 24.4 End-to-End Acceptance Flow

The primary acceptance test follows the `DESIGN.md` demo: Chiang Mai requests 20 units, Lampang is recommended, HQ approves, Lampang reserves/picks/packs/dispatches, Chiang Mai accepts 18 and records 2 damaged, the claim produces a replacement resolution, and all balances, ledger lines, KPIs, notifications, and audits reconcile.

## 25. Implementation Decomposition

This architecture is too large for one safe implementation batch. After design approval, create separate implementation plans in this order:

1. Foundation: database roles/schemas, Better Auth, profiles, RBAC, facilities, products, migrations, test harness.
2. Inventory core: balances, immutable ledger, idempotency, locks, stock read APIs.
3. Inbound operations: receiving, putaway, movement, adjustment, counts.
4. Transfer fulfillment: transfer approval, reservation, picking, packing.
5. Logistics: shipment, dispatch, events, POD, destination receiving.
6. Claims: evidence, SLA, investigation, resolution, stock effects.
7. Platform read models: notifications, audit search, dashboards, reports, exports.

Each phase must produce working APIs and integration tests before the next phase starts.

## 26. Decisions Locked by This Draft

- Clean-slate target; no compatibility layer for current Supabase browser code.
- Better Auth in `better_auth`; business data in private `app` schema.
- Next.js Route Handlers are the only browser-facing business API.
- Normalized documents plus append-only ledger and balance projection.
- UUIDv7 application-generated IDs and separate human document numbers.
- Command endpoints for transitions; no generic status patching.
- Permission plus facility scope enforced by application services.
- Idempotency and optimistic concurrency are part of the public API contract.
- Serverless transaction pooler assumptions are explicit.
- Full event sourcing, microservices, direct Data API business access, and hard delete of posted documents are excluded.
